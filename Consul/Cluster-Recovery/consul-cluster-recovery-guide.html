1. Master Decision Flowchart

Use this flowchart first to determine which recovery method applies to your situation.

2. Method 1 — Snapshot Recovery

Cleanest / Easiest

Use when you have a valid Consul snapshot (.snap file). Some data between the last snapshot and the crash may be lost.

1 Start a Fresh Cluster
Install Consul on all nodes with empty data directories. They will bootstrap on new IPs automatically via retry_join.
2 Verify Leader Election
consul operator raft list-peers
# or
curl http://127.0.0.1:8500/v1/status/leader
3 Restore Snapshot
# With management token
consul snapshot restore -token=<management-token> backup.snap

# Without token (if default_policy=allow temporarily)
consul snapshot restore backup.snap
Note: If ACLs were enabled on the old cluster, the snapshot contains the old ACL state. A valid management token from the old cluster must be passed. If unavailable, see Section 6.

3. Method 2 — Data Directory Recovery

Same IPs preferred

Use when a backup of the Consul data directory exists. Works best when restoring to same network topology. Requires peers.json if IPs have changed.

1 Copy data directory to each server
rsync -avz /backup/consul-data/ /opt/consul/data/
2 Start Consul on all servers
systemctl start consul
3 Verify cluster & ACL state
consul members
consul operator raft list-peers
Watch for: 403 (ACL not found) errors — this means the ACL bootstrap token is not available for the restored data. See Section 6.
Find leader without CLI (ACL blocked): curl http://127.0.0.1:8500/v1/status/leader
4 ACL Bootstrap error (if seen)
consul acl bootstrap
# Expected error:
# Failed ACL bootstrapping: 403 (ACL bootstrap no longer allowed (reset index: 274))
Follow the ACL Reset procedure in Section 6.
Note: bootstrap_expect is only considered for nodes with an empty data directory forming a new cluster. It has no effect when restoring from a backup.

3. Method 3 — peers.json Recovery

Last Resort

Use when healthy servers exist with intact Raft data but quorum cannot be reached — or when you are migrating to new IPs.

When peers.json is the only option

ScenarioWhy other methods failpeers.json fix
Last Node Standing
3-node cluster, 2 servers permanently lost		 Snapshot restore fails (no leader). Data dir restore fails (server waits for dead peers forever). Edit peers.json to contain only the surviving server. It elects itself leader (1/1 votes).
IP Migration
Restored data dirs on servers with new IPs		 Raft database has old IPs hardcoded. New servers endlessly try to reach dead IPs. peers.json overwrites the network topology with new IPs before start.

peers.json Format — v3 (Most Common)

[
  {
    "id": "node-id-from-server-1",
    "address": "192.168.1.10:8300",
    "non_voter": false
  },
  {
    "id": "node-id-from-server-2",
    "address": "192.168.1.11:8300",
    "non_voter": false
  },
  {
    "id": "node-id-from-server-3",
    "address": "192.168.1.12:8300",
    "non_voter": false
  }
]

peers.json Format — v2 (Legacy)

["192.168.1.10:8300", "192.168.1.11:8300", "192.168.1.12:8300"]
Critical Rules:
  • Only include servers that survived the outage — never include dead nodes.
  • Get the Node ID from: cat /opt/consul/data/node-id
  • In Consul ≥ 0.7, peers.json is auto-deleted after ingestion.

Useful Commands to Gather Info

# Check Raft protocol version
consul members -detailed | grep raft_vsn

# List peers
consul operator raft list-peers

# Autopilot state (find highest Last Term/Index)
consul operator autopilot state -stale

# If Consul CLI blocked by ACL — get leader via API
curl http://127.0.0.1:8500/v1/status/leader

5. Scenario: New IPs + Have Both Data Dir & Snapshot

All 3 nodes crashed. You have a backup data directory AND a snapshot. You must bring up 3 new nodes with new IP addresses.

Option 1 — peers.json Method Zero Data Loss

Preserves all state right up to the moment of crash — including KV writes that happened after the last snapshot.

  1. Install Consul, copy old data dirs to new servers. Do not start Consul yet.
  2. Read node-id from each new server: cat /opt/consul/data/node-id
  3. Create peers.json in /opt/consul/data/raft/ on every new server with new IPs + node IDs.
  4. Start Consul on all 3 nodes simultaneously.
  5. Verify: consul operator raft list-peers
Option 2 — Snapshot Method Easiest / Clean

Accepts minor data loss (delta between last snapshot and crash). No JSON files needed. Works perfectly with new IPs.

  1. Start 3 new servers with empty data dirs. They bootstrap cleanly on new IPs.
  2. Wait for leader election.
  3. Run: consul snapshot restore backup.snap
  4. Verify cluster state.
Why new IPs work: Snapshot contains the Consul state machine, not the raw Raft peer logs — so old IPs are never introduced to the new cluster's routing table.

6. ACL Recovery Procedures

Key Principle: ACL recovery can only happen after the cluster has a leader. Complete peers.json or snapshot recovery first, then address ACL issues.

ACL Reset Step-by-Step

1 Find the leader
curl http://127.0.0.1:8500/v1/status/leader
# Example output: "192.168.1.10:8300"
# SSH into the server matching that IP
2 Trigger bootstrap to get Reset Index
consul acl bootstrap
# Expected error output:
# Failed ACL bootstrapping: Unexpected response code: 403
# (Permission denied: ACL bootstrap no longer allowed (reset index: 274))
Save the reset index number — you will need it in the next step.
3 Write Reset Index to disk (on the leader)
echo 274 > /opt/consul/data/acl-bootstrap-reset
4 Generate new bootstrap token
consul acl bootstrap
# Output:
# AccessorID:   e85b9b9a-4c28-9d43-09ef-d4928f6412ab
# SecretID:     a23b8f2d-df71-46bb-be0c-51928374a9bc
# Description:  Bootstrap Token (Global Management)
# Policies:     00000000-0000-0000-0000-000000000001 (global-management)
Consul auto-deletes acl-bootstrap-reset from disk after use. Export the SecretID as your new CONSUL_HTTP_TOKEN.

ACL Config: enabled=true allow vs enabled=false

Setting ACL Engine Requests without token ACL API / bootstrap works? Use for recovery?
enabled=true
default_policy="allow"		 ON (permissive) Allowed (fall-through) YES — ACL endpoints active Yes — preferred
enabled=false OFF Allowed (no checks) NO — ACL API disabled No — cannot bootstrap

7. Kubernetes-Specific peers.json Steps

Do NOT delete or recreate pods after creating peers.json. Pod rescheduling changes IPs and invalidates the file.
1 Identify healthiest server pod
kubectl exec -n consul -it consul-server-0 -- consul members
kubectl exec -n consul -it consul-server-0 -- consul operator autopilot state -stale
Pick the pod with highest Last Term and Last Index.
2 Generate peers.json (v3 — standard)
kubectl exec -n consul -it consul-server-0 -- \
  sh -c 'curl -s localhost:8500/v1/agent/members | \
  jq "[ .[] | select(.Tags.role == \"consul\" and .Status == 1) | \
  {id: .Tags.id, address: \"\(.Addr):\(.Port)\", non_voter: false} ]" \
  > /consul/data/raft/peers.json'
2b Generate peers.json (v3 — ACL/TLS enabled)
kubectl exec -n consul -it consul-server-0 -- \
  sh -c 'curl -s -k https://localhost:8501/v1/agent/members | \
  jq '\''[ .[] | select(.Tags.role == "consul" and .Status == 1) | \
  {id: .Tags.id, address: "\(.Addr):\(.Port)", non_voter: false} ]'\'' \
  > /consul/data/raft/peers.json'
3 Verify peers.json on each running pod
kubectl exec -n consul -it consul-server-0 -- cat /consul/data/raft/peers.json
kubectl exec -n consul -it consul-server-1 -- cat /consul/data/raft/peers.json
kubectl exec -n consul -it consul-server-2 -- cat /consul/data/raft/peers.json
4 Gracefully stop Consul process (in-place)
# Preferred
consul leave -token=<bootstrap_or_management_token>

# Fallback if ACL error "403 ACL system must be bootstrapped"
pkill consul
pkill consul causes the container to restart in-place, preserving the pod IP. The container is managed by Kubernetes and will be restarted automatically.
5 Verify recovery
kubectl exec -n consul -it consul-server-0 -- consul operator raft list-peers
Confirm: leader present, all servers show Voter: true, RaftProtocol version matches config.
