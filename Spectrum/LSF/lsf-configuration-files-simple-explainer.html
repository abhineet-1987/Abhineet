Week 1 Reference

LSF Configuration Files — Simply Explained

IBM Spectrum LSF 10.1.0  ·  What every config file does, where it lives, and when you edit it

1 The Mental Model — Two Layers, Two Directories

LSF config files split into two layers. Think of them as the foundation and the rules:

$LSF_CONFDIR  (Base Layer) Describes the cluster itself — what hosts exist, what resources are defined, global env settings. Read by LIM and the base daemons.
$LSB_CONFDIR/<cluster>/configdir  (Batch Layer) Describes the workload rules — queues, job limits, user shares, resource policies. Read by mbatchd and mbschd.
$LSF_CONFDIR/ ← Base layer ├── lsf.conf ★ The master config ├── lsf.shared Resource/host-type dictionary └── lsf.cluster.<name> Host roster + admins $LSB_CONFDIR/<cluster>/configdir/ ← Batch layer ├── lsb.params Global batch tuning knobs ├── lsb.queues ★ Queue definitions ├── lsb.hosts Per-host scheduling rules ├── lsb.users User groups & fair share ├── lsb.resources Resource limits & allocation ├── lsb.applications App-specific job profiles └── lsb.modules Scheduler plug-in modules
Ownership rule: lsf.conf is owned by root. All other config files are owned by the primary LSF administrator, and are readable by all cluster users.

2 Base Layer — Cluster Foundation Files

lsf.conf ★ Most Critical in $LSF_ENVDIR (usually /etc)
The master config file for the entire cluster. It tells every daemon where everything else is — directories, binaries, logs. If LSF can't find this file, nothing starts.
  • Sets all path variables: LSF_CONFDIR, LSB_CONFDIR, LSF_LOGDIR, LSB_SHAREDIR
  • Sets the cluster name, master host selection, and authentication method
  • Controls global feature toggles (cgroups, EGO, multicluster, SSL)
  • Sets log verbosity levels (LSF_LOG_MASK)
LSF_TOP="/usr/share/lsf" LSF_CONFDIR="$LSF_TOP/conf" LSB_CONFDIR="$LSF_TOP/conf/lsbatch" LSF_LOGDIR="$LSF_TOP/log" LSF_CLUSTER_NAME="bootcamp" LSF_MASTER_LIST="lsfmgr"
lsf.shared Base Layer in $LSF_CONFDIR
The cluster dictionary. Defines all the named concepts LSF knows about — host types, host models, and custom resources like GPUs or licenses. Think of it as registering vocab before using it anywhere else.
  • Cluster section — lists all clusters (one line per cluster)
  • HostType section — names for OS/arch combos (e.g. LINUX64, X86_64)
  • HostModel section — CPU model names and speed factors (used for fair scheduling)
  • Resource section — declares custom resources like gpu, license1, scratch
Begin Resource RESOURCENAME TYPE INTERVAL INCREASING DESCRIPTION gpu Numeric 60 N (Number of GPU cards) license1 Numeric 60 N (App license count) End Resource
lsf.cluster.<clustername> Base Layer in $LSF_CONFDIR
The host roster. Lists every host in the cluster, its type/model, and whether it's a server (can run jobs) or client (submit-only). Also names the LSF administrators.
  • Administrators section — who has lsadmin/badmin authority
  • Hosts section — hostname, host type, host model, server flag (1=server, 0=client-only)
  • Management host candidates are marked here (failover priority)
Begin Host HOSTNAME model type server RESOURCES lsfmgr IntelI7 LINUX64 1 (mg) lsfexec1 IntelI7 LINUX64 1 () lsfexec2 IntelI7 LINUX64 1 () End Host

3 Batch Layer — Workload Rules Files

lsb.queues ★ Most Critical in $LSB_CONFDIR/<cluster>/configdir
Defines every job queue and its rules. A queue is a named bucket for jobs, with its own priority, limits, allowed users, allowed hosts, and scheduling policy. This is the file you'll edit most often.
  • PRIORITY — higher number = dispatched first
  • HOSTS — which exec hosts can run jobs from this queue
  • USERS — who can submit to this queue
  • RUNLIMIT — max wall-clock time a job can run
  • RES_REQ — default resource requirements for all jobs in queue
  • MAX_JOBS — max concurrent running jobs in this queue
  • DISPATCH_WINDOW — time windows when queue is active
  • FAIRSHARE — enable user-fair-share within this queue
Begin Queue QUEUE_NAME = normal PRIORITY = 30 RUNLIMIT = 1:0 # 1 hour USERS = all HOSTS = all DESCRIPTION = Default queue for normal jobs End Queue
lsb.params Batch Layer in $LSB_CONFDIR/<cluster>/configdir
The global batch tuning file. Contains cluster-wide settings that apply to all queues and all jobs — not specific to any one queue or host.
  • DEFAULT_QUEUE — which queue jobs go to if user doesn't specify one
  • MAX_JOB_NUM — maximum number of jobs (running + pending) in the system
  • CLEAN_PERIOD — how long finished job records stay in memory
  • MBD_SLEEP_TIME — scheduling cycle interval (seconds)
  • CONDENSE_PENDING_REASONS — condense pending reason display in bjobs
  • JOB_ACCEPT_INTERVAL — seconds between dispatch cycles per host
Begin Parameters DEFAULT_QUEUE = normal MAX_JOB_NUM = 10000 MBD_SLEEP_TIME = 10 CLEAN_PERIOD = 3600 End Parameters
lsb.hosts Batch Layer in $LSB_CONFDIR/<cluster>/configdir
Per-host batch settings. Lets you override scheduling thresholds, set job slot limits, and define dispatch windows per host — independent of any queue.
  • MXJ — max concurrent job slots on this host (e.g. ! = use CPU count)
  • DISPATCH_WINDOW — time windows when this host accepts jobs
  • Load thresholds: loadSched / loadStop — at what CPU/mem load to stop dispatching or suspend
  • RES_REQ — additional resource requirements for any job on this host
Begin Host HOST_NAME MXJ loadSched loadStop DISPATCH_WINDOW lsfexec1 4 - - () lsfexec2 ! 3.5/3.5 - (5:30-22:00) End Host
lsb.users Batch Layer in $LSB_CONFDIR/<cluster>/configdir
Defines user groups and fair-share policies. Controls how much cluster capacity each user or team can consume.
  • Defines named user groups (e.g. devteam, analysts)
  • Sets hierarchical fair-share trees — shares determine scheduling priority when competing for resources
  • MAX_JOBS per user or group — hard cap on concurrent running jobs
  • MAX_PEND_JOBS — cap on pending jobs per user
Begin UserGroup GROUP_NAME GROUP_MEMBER devteam (alice bob charlie) End UserGroup
lsb.resources Batch Layer in $LSB_CONFDIR/<cluster>/configdir
Defines resource allocation limits — cluster-wide caps on how much of a shared resource any user, project, queue, or application can consume at once.
  • Limit sections — e.g. "no user can hold more than 100 GPU slots"
  • Can scope limits by user, queue, host, project, or application
  • Also configures resource export/import for multicluster setups
Begin Limit NAME = gpu_cap PER_USER = all QUEUES = gpuq SLOTS = 32 End Limit
lsb.applications Optional in $LSB_CONFDIR/<cluster>/configdir
Defines named application profiles. When many jobs of the same type (e.g. MPI, Python ML) always need the same resource settings, you package those settings into a named profile so users don't have to repeat them at submission time.
  • Pre-set RES_REQ, RUNLIMIT, MEMLIMIT, pre/post-execution scripts per app
  • Users submit with bsub -app myprofile myjob
  • Set a default profile with DEFAULT_APPLICATION in lsb.params
Begin Application NAME = mpi_app RES_REQ = span[ptile=16] MEMLIMIT = 8192 # MB per process PROCLIMIT = 64 End Application
lsb.modules Advanced in $LSB_CONFDIR/<cluster>/configdir
Lists the scheduler plug-in modules that mbschd loads. If this file is absent or empty, LSF uses the default scheduler module (schmod_default). You rarely need to edit this unless enabling advanced features like fairshare or reservation plug-ins.

5 The Safe Change Workflow — Always Do This

Golden rule: Always check before you apply. A config error that reaches a running daemon can cause daemon restarts or job failures.
# 1. Edit the config file vi $LSB_CONFDIR/bootcamp/configdir/lsb.queues # 2. Lint check — catch errors BEFORE touching live daemons badmin ckconfig -v # → "No errors found" ✓ safe to proceed # → "Error in line 42" ✗ fix the file first # 3. Apply without downtime badmin reconfig # hot-reload for most batch files # OR — if you changed lsb.params or need a full restart: badmin mbdrestart # reads lsb.events on restart — may take time # For base-layer files (lsf.conf, lsf.shared, lsf.cluster.*): lsadmin ckconfig -v # check first lsadmin reconfig # apply

6 How the Files Relate to Each Other

Files at different layers reference each other. Here's the dependency chain:

lsf.conf → defines where all other files live (the anchor) ↓ lsf.shared → declares resource names and host-type names used everywhere ↓ lsf.cluster.* → assigns hosts to types/models defined in lsf.shared ↓ lsb.queues → references hostnames, resource names from lsf.shared lsb.hosts → references hostnames from lsf.cluster.* lsb.users → defines groups referenced by lsb.queues (USERS param) lsb.resources → references queues from lsb.queues, users from lsb.users lsb.applications → profiles referenced at bsub time via -app flag
Common mistake: Defining a resource in lsb.queues (RES_REQ=rusage[gpu=1]) but forgetting to declare gpu in lsf.shared first. The result is a ckconfig error: "resource not defined".
