1 LSF Architecture in Plain English

Think of LSF as a job post office. Users drop off jobs (letters). A central manager sorts and dispatches them to the right workers. Workers run the jobs and report back.

The Big Picture

User
bsub
→
Management Host
mbatchd + mbschd
→
Exec Host 1
sbatchd + res
 
Exec Host 2
sbatchd + res
 
Exec Host N
sbatchd + res
Every Host runs:  lim (health reporter)  +  pim (process watcher)  +  res (job launcher)

2 The 6 Daemons — Who Does What

Daemon Full Name Runs On Simple Role
mbatchd Management Batch Daemon Manager only The job registry. Accepts all job submissions, holds them in queues, dispatches them to workers. Single source of truth for all job state.
mbschd Management Batch Scheduler Daemon Manager only The brain. Works alongside mbatchd to decide which job runs on which host and when. Makes all scheduling decisions.
sbatchd Slave Batch Daemon Every exec host The local foreman. Receives dispatch orders from mbatchd, starts and monitors jobs on the local host, reports status back. Forks one child per job.
res Remote Execution Server Every exec host The job launcher. Creates the execution environment (user, env vars, directories) in which each job actually runs. Called by sbatchd's child.
lim Load Information Manager Every host The health reporter. Constantly collects CPU, memory, disk, and I/O metrics. Reports them up to mbatchd so the scheduler can pick lightly-loaded hosts.
pim Process Information Manager Every exec host The resource cop. Tracks CPU/memory used by each running job process. Used to enforce resource limits and fair-share policy. Started and watched by lim.
Tip — startup order to remember: When you run lsfstartup, you will see:
LIM started → RES started → sbatchd started
On the manager, mbatchd/mbschd also start. LIM always comes up first because everyone else depends on it.

3 Key Environment Variables & Directories

LSF is directory-driven. If a path variable is wrong, daemons refuse to start. Know these cold.

Variable What it points to Why it matters
LSF_ENVDIR /etc (default) Where LSF looks for lsf.conf. The most critical variable. Wrong path = nothing starts.
LSF_CONFDIR LSF_TOP/conf All LSF configuration files live here (lsf.cluster.*, lsf.shared, etc.)
LSB_CONFDIR LSF_TOP/conf/lsbatch Batch-specific config files: lsb.queues, lsb.hosts, lsb.params, etc.
LSF_LOGDIR LSF_TOP/log All daemon error logs. Must be owned by root. If missing/broken, logs fall back to /tmp.
LSB_SHAREDIR LSF_TOP/work Job history files: lsb.events and lsb.acct live here.
Most common Day-1 mistake: Daemon fails to start and logs land in /tmp instead of LSF_LOGDIR. Always check LSF_LOGDIR ownership (ls -ld $LSF_LOGDIR) first.

The Master Config File: lsf.conf

This is the most important file in LSF. It lives in $LSF_ENVDIR/lsf.conf and tells every daemon where everything else is. If LSF can't find it, nothing works.

# Typical lsf.conf entries you will see LSF_TOP="/usr/share/lsf" LSF_CONFDIR="$LSF_TOP/conf" LSB_CONFDIR="$LSF_TOP/conf/lsbatch" LSF_LOGDIR="$LSF_TOP/log" LSB_SHAREDIR="$LSF_TOP/work" LSF_CLUSTER_NAME="bootcamp"

4 Start / Stop / Reconfigure Commands

Two admin tools control everything. Only LSF administrators or root can run them.

Command Controls What it does
lsadmin lim, res Start/stop/restart the base LSF layer daemons
badmin sbatchd, mbatchd Start/stop/restart the batch layer daemons
lsfstartup All daemons Start all LSF daemons at once (used at system boot / initial setup)

The Config Check → Reconfigure Workflow

Always check before you reload. Never reload with errors.

# Step 1 — Check for errors BEFORE applying changes lsadmin ckconfig -v # checks lsf.conf, lsf.cluster, lsf.shared badmin ckconfig -v # checks lsb.queues, lsb.hosts, lsb.params etc. # Step 2 — Apply if clean lsadmin reconfig # reload LIM config (no restart needed) badmin reconfig # reload batch config (no restart needed) badmin mbdrestart # full mbatchd restart (reads lsb.events too — may be slow)
Remember: ckconfig = lint check. reconfig = hot-reload. mbdrestart = full restart. Use them in that order.

Raising Debug Log Levels (temporary)

# Increase mbatchd verbosity for one investigation, then revert badmin diagnose -c all -l 2 # raise mbatchd log class detail # ... reproduce the issue ... badmin diagnose -c all -l 0 # revert to normal

Scheduler Profiling

# In lsf.conf, add temporarily: LSB_PROFILE_MBD=Y # Then: badmin mbdrestart # Profile timing lines appear in mbatchd.log — grep for "PROFILE:" # Remove the param and restart when done.

5 Job Lifecycle — From bsub to DONE

Every LSF job passes through states. Understanding the state transitions is how you debug 80% of support tickets.

bsub
→
PEND
→
RUN
→
DONE
 or 
EXIT
Suspensions:   PSUSP (pending suspended)   USUSP (user suspended)   SSUSP (system suspended)

State Meanings

StateMeaningWhat to check
PENDWaiting in queue to be scheduledbjobs -p <jobid> shows the reason — no free slots, resource unavailable, queue policy, etc.
RUNDispatched and executing on a hostbjobs -l <jobid> shows exec host, start time, resource usage so far
DONEFinished with exit code 0Healthy completion. Check output file.
EXITFinished with non-zero exit codebhist -l <jobid> shows exit reason, exit code, and log evidence
SSUSPSuspended by LSF (load threshold crossed)Host load too high. LSF auto-resumes when load drops.
USUSPSuspended by user (bstop)User ran bstop <jobid>. Resume with bresume <jobid>.

The 5 Steps LSF Takes for Every Job

1. SUBMIT User runs bsub → mbatchd receives and assigns a Job ID → job state = PEND 2. SCHEDULE mbschd evaluates queue policies, resources, fair-share → picks a host 3. DISPATCH mbatchd sends job to target sbatchd → sbatchd forks child → res sets up env 4. EXECUTE Job runs under the user's identity on the exec host 5. COMPLETE sbatchd reports exit status to mbatchd → state = DONE or EXIT Event written to lsb.events, accounting written to lsb.acct

6 Log Files — Where Evidence Lives

Every daemon writes its own log. Knowing which log to look in first saves minutes on every ticket.

Log FileDaemonHostWhat you'll find there
mbatchd.log.<mgr>mbatchdManagerJob submissions, dispatch decisions, queue operations, errors affecting all jobs
mbschd.log.<mgr>mbschdManagerScheduling cycle details, why jobs stayed PEND, scheduler profiling output
sbatchd.log.<host>sbatchdEach exec hostJOB_START, JOB_EXIT, exit codes, per-host job execution events
lim.log.<host>limEvery hostLoad index updates, LIM heartbeat, host join/leave events
res.log.<host>resEvery exec hostRemote execution requests, connection errors, env setup
pim.log.<host>pimEvery exec hostProcess tracking, resource limit enforcement events

Event & Accounting Files

FileLocationPurposeKey command
lsb.events $LSB_SHAREDIR/<cluster>/logdir/ Real-time event journal. Every job state change is appended here. Used by mbatchd on restart to reconstruct state. bhist -l <jobid>
lsb.acct same directory Accounting record. Written when a job finishes. Contains resource usage, start/end time, exit status. bacct -l <jobid>
Troubleshooting shortcut: Start with mbatchd.log (what happened cluster-wide?) → then sbatchd.log.<host> (what happened on the exec host?) → then bhist -l <jobid> (what does LSF's own record say?).

8 Break/Fix Scenarios to Know

SymptomRoot CauseFix
Daemons won't start; logs in /tmp LSF_LOGDIR has wrong ownership or permissions chown root $LSF_LOGDIR && chmod 755 $LSF_LOGDIR, then restart
All daemons fail silently on startup lsf.conf missing or LSF_ENVDIR points to wrong directory Verify ls $LSF_ENVDIR/lsf.conf exists; correct symlink if needed
sbatchd starts but mbatchd does not Manager's LIM is temporarily unknown; management host unreachable Run lsid — if LIM is down, fix LIM first, then mbatchd will reconnect
Jobs stay PEND on a cluster that looks healthy Host not in queue's hostlist, or mbatchd doesn't see the worker Check bhosts, verify host is in queue's HOSTS parameter in lsb.queues
